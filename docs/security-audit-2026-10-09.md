# Аудит безопасности v2gr1.ru — 9 октября 2026

## Область и ограничения

Проверены исходники Next.js/Prisma, API авторизации и администратора, оформление и подтверждение платежей, загрузки, HTML/JSON-LD, HTTP middleware, Docker Compose, Nginx проекта, права PostgreSQL, алгоритмы хранения паролей, зависимости npm и доступность закрытых URL без авторизации. Выполнены локальные регрессионные тесты и безопасные проверки работающего сайта.

Это аудит доступной конфигурации и кода, а не гарантия отсутствия всех уязвимостей. Не проводились нагрузочные/разрушительные атаки, реальные платежи, отправка тестовых сообщений клиентам, подбор паролей, аудит гипервизора Timeweb или других проектов на VPS. Наличие UFW inactive не доказывает отсутствие внешнего firewall Timeweb. Публичная доступность чужих портов извне отдельно не проверялась.

## Пароли, база и шифрование

- В БД 9 пользователей: у всех bcrypt `$2a$12$`, у всех 9 различные соли. Соль встроена в хеш; отдельно хранить её не нужно.
- Новый пароль сначала преобразуется HMAC-SHA256 с PASSWORD_PEPPER, затем bcrypt cost 12. Серверный pepper имеет длину не менее 32 символов; содержимое не выводилось.
- Сохранена совместимость со старыми bcrypt без pepper: после успешного входа старый хеш обновляется. По одному префиксу bcrypt нельзя установить, какие существующие записи уже используют pepper.
- Пароли хешируются, а не обратимо шифруются. Имена, телефоны, email, адреса и заказы в PostgreSQL — обычные поля, шифрования полей нет.
- Сессионные токены: 32 случайных байта, в базе только SHA-256. Cookie HttpOnly, Secure на HTTPS, SameSite=Strict, префикс __Host, TTL 8 часов с продлением. MFA для администратора отсутствует.
- Роль сайта printlab_app: не superuser, не владелец БД, без CREATEDB/CREATEROLE, без CREATE в public и без создания схем. База магазина не публикует порт на хост.
- Соединение web→PostgreSQL внутри Docker без TLS. Интернет→сайт использует HTTPS; это разные уровни защиты.
- Корневой том гостевой ОС — ext4 без видимого dm-crypt/LUKS. Шифрование хранилища на стороне Timeweb не подтверждено. Пользователь сообщил, что отдельно шифрование БД не включал.
- `.env` имеет права 0600. Серверные ключи не передаются в браузер. Ключ Яндекс Карт публичен по назначению; ограничения доменов и квоты проверяются в кабинете Яндекса.

## SQL-инъекции

Комментарий заказа сохраняется через Prisma `order.create` как данные. Конкатенации пользовательского ввода в SQL в приложении не обнаружено. Два raw-запроса — tagged templates: лимиты API и healthcheck. Присланная пользователем строка безопасно передана параметром в read-only SELECT: получена обратно без исполнения.

Сборка запускает `scripts/check-sql-safety.cjs`: запрещены unsafe SQL API, прямой Prisma.raw и вызов raw-query в обычной форме вместо inline tagged template. Это профилактическая статическая проверка, не доказательство безопасности произвольного будущего кода и не замена code review.

SQL-слова в комментариях не удаляются: блокировка слов SELECT/DROP не защищает от инъекций, а параметризация позволяет корректно хранить обычный текст.

## Проверенные существующие меры

- Административные API проверяют сессию и роль ADMIN; заказ покупателя выбирается с фильтром userId.
- Цена и итог заказа рассчитываются сервером; дополнительные поля paymentStatus/totalInKopecks/userId от покупателя не принимаются схемой.
- Подтверждение YooKassa запрашивается у провайдера с серверными credentials, не берётся на веру из webhook.
- Telegram webhook проверяет секрет timingSafeEqual и разрешённые user IDs.
- Формы имеют ограничения длин и типов. Вход ограничен по IP, глобально и по аккаунту. Арифметическая captcha — слабая защита от автоматизации, не полноценный антибот.
- HTML писем экранируется; комментарии React выводятся как текст; Telegram-заказы — plain text.
- CSP nonce/strict-dynamic, HSTS, nosniff, frame-ancestors none, X-Frame-Options DENY присутствуют.
- Web работает не от root, cap_drop ALL, no-new-privileges. PostgreSQL изолирован от публичных портов.

## Оставшиеся риски и действия владельца

1. **Высокий приоритет: резервное копирование и восстановление.** Защищённая внешняя копия и регулярная проверка восстановления не подтверждены. Организовать pg_dump в зашифрованный архив с публичным ключом получателя, хранить копии вне VPS; приватный ключ держать вне сервера. Хранение ключа вместе с архивом на одном VPS не защищает от полного захвата сервера. Бэкапы панели Timeweb проверить отдельно: периодичность, срок хранения, возможность восстановления и шифрование.
2. **Высокий приоритет: соседние проекты VPS.** На всех интерфейсах слушают другие сервисы, в том числе PostgreSQL другого проекта (5432), панели/приложения (3001, 3100, 5174, 8080, 8088, 8010, 8011 и др.). UFW inactive. Не закрывались: это чужие относительно магазина контейнеры, зависимости/потребители не известны. Нужен отдельный перечень необходимых публичных портов; закрыть остальные в Docker и firewall Timeweb, административный доступ через VPN/allowlist. Взлом соседнего сервиса может затронуть общий хост.
3. **Шифрование данных на диске.** Для защиты от кражи диска/снапшота нужна миграция на зашифрованный том/сервис либо шифрование чувствительных полей с ключом отдельно от БД. Не включалось на работающем root-диске без резервной копии и плана загрузки/восстановления. При полном доступе атакующего к приложению доступные ему данные всё равно можно расшифровать.
4. **MFA.** Для админов сайта отсутствует второй фактор. Уникальные пароли и MFA для Timeweb, почты, Telegram и платёжного кабинета обязательны как операционная мера; настройки этих аккаунтов не проверены.
5. **Доступ к загруженным моделям.** Ссылки с UUID остаются bearer-ссылками: знающий URL может скачать файл. Для конфиденциальных проектов нужны закрытое хранилище, авторизация и ограниченные по времени ссылки; печатный агент сейчас забирает файлы по URL.
6. **SSH: высокий приоритет.** Эффективная конфигурация sshd разрешает PermitRootLogin=yes и PasswordAuthentication=yes. Перед отключением входа по паролю нужно подтвердить рабочий SSH-ключ/консоль восстановления. Вопрос владельцу задан; доступ автоматически не менялся.
7. **Мониторинг и обслуживание.** Не проверены контейнерные CVE сканером образов, настройки гипервизора, внешние правила SSH и историю входов, внешний WAF/DDoS, журналы за весь срок эксплуатации. Отсутствие признаков в проведённых проверках не доказывает отсутствие прежнего взлома. Нужны регулярные обновления, контроль места, ошибок входа и бэкапов.
8. **Регистрация и email.** Подтверждение владения email при регистрации отсутствует. Возможны регистрации с чужим адресом и нежелательные письма после связанных действий. Нужна отдельная схема email verification без блокировки уже существующих покупателей.

## Проверки

- 37 тестов в 8 файлах прошли: XSS/JSON-LD, Origin/CSRF, redirect, password salt/pepper, параметры заказа, проверка платежей и прежние регрессионные тесты.
- TypeScript typecheck и production build прошли. Осталось прежнее предупреждение CSS autoprefixer про align-items:end, не относящееся к безопасности.
- npm audit --include=dev: 0 известных уязвимостей по текущему lockfile (186 зависимостей с учётом optional/dev).
- Все 23 обнаруженных административных HTTP-метода без сессии вернули 403.
- После развёртывания: health 200; checkout без сессии 401; Origin атакующего с поддельным forwarded host и prefetch-заголовками 403; ошибочный JSON регистрации 400; /.env и /.git/config 404.
- Порт прокси фактически привязан к 127.0.0.1:32741. PostgreSQL магазина без опубликованного порта.
- SMTP verify с обязательным TLS и аутентификацией прошёл; писем не отправлялось.
- Безопасный read-only SQL roundtrip подтвердил сохранение присланной строки как параметра.
- Изменения приложения развёрнуты в существующем контейнере v2gr1.ru. Рабочая база не использовалась для разрушительных проб; реальные платежи и новые заказы не создавались.
- Root SSH по паролю не отключён: подтверждение работоспособного SSH-ключа пока не получено.
- Фактические отправка заказа в СДЭК/скачивание накладной и платёж после обновления не выполнялись; проверки платёжных атрибутов покрыты тестами с mock-ответами провайдера.
